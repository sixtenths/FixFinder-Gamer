## DOOM port and memory

- V8 links against 128 KiB SRAM and a 512 KiB flash region. GigaDevice documents 192 KiB AHB SRAM in three banks and 64 KiB of CPU-only TCM. The game linker must account for the split. DMA buffers belong in AHB SRAM. [GigaDevice GD32F427xx datasheet](https://www.gd32mcu.com/data/documents/datasheet/GD32F427xx_Datasheet_Rev1.9.pdf)
- A full 240 x 320 RGB565 framebuffer costs 153,600 bytes. A 320 x 200 indexed frame costs 64,000 bytes and a 320-pixel RGB565 conversion line costs 640 bytes. If the controller supports a landscape window, the original image dimensions fit with 20 lines above and below. Streaming converted lines keeps the RGB565 buffer small.
- The full uncompressed shareware IWAD exceeds the 3 MiB internal flash capacity before engine code. Photo 265 shows a Kingston `EMMC04G-M627` at U11, a 4 GB eMMC. Verify its wiring and existing layout read-only before considering asset placement. [Kingston eMMC part table](https://media.kingston.com/pdfs/emmc/emmc-product-flyer-us.pdf), [STM32F427 GBADoom port](https://github.com/NilsN3DP/Prusa-Core-One._But-Can-it-run-Doom)
- The STM32F427 GBADoom port provides a starting point for a flash-mapped E1M1 build from locally prepared assets. The nRF52840 port is a Cortex-M4 and 256 KiB reference. GBADoom retains pointers into some level lumps, so streaming the full episode from eMMC requires a storage design that keeps those pointers valid. [GBADoom](https://github.com/doomhack/GBADoom), [nRF52840 Doom](https://github.com/next-hack/nRF52840Doom), [GBADoom WAD pointer analysis](https://github.com/atc1441/saphe-t_DOOM#how-it-works)
- Cross-compiled 56 engine sources from GBADoom revision `25deefdb44427e068735d3ef2af1e9a44d5cac85` into a Cortex-M4 relocatable object. This revision uses the byte RGB palette API expected by the Prusa backend. The current GBADoom tip uses a 16-bit palette API. Reproduce with `scripts/Check-DoomEngine.ps1 -EngineSource <checkout>`. Arm GCC 15.2 used GNU C23 and a forced `stdint.h` include. This compile check suppresses legacy pointer and implicit-declaration diagnostics and leaves a const-qualifier warning in `st_stuff.c`. A final link needs the display and input backend, timing, audio stubs, WAD conversion, and runtime services.
- The engine object reported 1,318,492 bytes of text/read-only data, 57 bytes of initialized data and 23,345 bytes of BSS. The Prusa reducer at `1b791ccd23d4c95d4eb4a0991ae0192f22730739` turned the upstream 4,196,020-byte shareware IWAD into a 1,263,828-byte E1M1 candidate kept under ignored `build/`. Together the engine's static flash sections and the reduced raw WAD total 2,582,377 bytes. This is a preliminary flash estimate. The final WAD layout, runtime heap, stack and linked image still require measurement. [Pinned GBADoom source](https://github.com/doomhack/GBADoom/tree/25deefdb44427e068735d3ef2af1e9a44d5cac85), [Prusa WAD reducer](https://github.com/NilsN3DP/Prusa-Core-One._But-Can-it-run-Doom/blob/1b791ccd23d4c95d4eb4a0991ae0192f22730739/tools/reduce_doom.py)
